# Plan 02-01: Events and invite links

## Phase Goal

> ROADMAP `**Goal:**` (verbatim, not in user-story format): "Signed-in users can create an event, invite family with a link, keep a personal wishlist, choose which wishes to share into which events, and browse what the other members wish for." MVP mode is on, but the Goal line is not an As a / I want to / so that story. No story is invented here; run `/gsd-mvp-phase 2` if a user-story Goal is wanted.

Plan 1 of 2 in Phase 2. This plan ships the events half of the phase as a vertical slice: create an event, see it in My events, send its invite link, and have a relative join through an explicit confirm. Plan 02-02 (wave 2) adds wishes, sharing and browsing on top of the event page built here.

<objective>
Signed-in users can create an event, see all their events at /events/, open the event page with its members, copy the invite link, and bring relatives in through /invite/<token>/. Opening the link never joins anyone; only the Join POST does. A signed-out relative goes through the Google sign-in and lands back on the confirm page, with a session fallback if next is lost. The privacy policy is updated before any of this can ship.

Purpose: EVNT-01..EVNT-05. Covers decisions D-01, D-02, D-03, D-04, D-13, D-14 (Events and Sign out; My wishlist is added in 02-02), D-15 (members list part) and D-16 (events and members part). Fixes review finding IN-08 (safe next for signed-in visitors), which the invite round trip needs.
Output: Event and Membership models with migration 0002, EventForm, event and invite views, five templates, navbar, privacy update, tests, two live smoke checks.
</objective>

## Assumption-delta decision

<assumption_delta_decision>
Detector fired on the phase scope (signals: pluralization "fallback", optional "optional", chosen "choose").
- pluralization (session fallback next to `next`). Primary noun: the invite token in the URL path. `next` carries the visitor back to /invite/<token>/; the session key `pending_invite` is a second carrier of the same token. Decision: add-alongside, accepted on purpose. Both carriers lead only to the confirm page, which still needs an explicit Join POST, and the session copy is popped on first use. A promote would be forced if a third entry path appeared (for example an emailed invite), at which point a single "pending invite" resolver should own every path.
- optional (event date). Primary noun: Event identified by pk and invite_token; the date is only a sort key and display field. Decision: no-change, because the date was never an identity anchor.
- chosen (which wishes go into which events): recorded in plan 02-02, where sharing is built.
</assumption_delta_decision>
