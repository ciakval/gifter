# Plan 01-01: Walking skeleton — Google sign-in round trip on Django 6.1

## Phase Goal

> ROADMAP `**Goal:**` (verbatim, not in user-story format): "Anyone with a Google account can sign in to Gifter at https://gifter.remesh.cz. The site runs on a cleaned-up Django 6.1 codebase that redeploys automatically from `main`."
>
> MVP mode asks for an "As a / I want to / so that" story, but the ROADMAP goal is not written that way and the planner must not invent one. Run `/gsd-mvp-phase 1` to reframe it if wanted; the plans below are derived from the goal and success criteria as written.

## Acceptance Criteria (phase-level, this plan's share)

- [ ] Django 6.1 app with five pinned runtime dependencies (OPS-01)
- [ ] Settings from env, fail-closed, `check --deploy` clean (OPS-02)
- [ ] Google is the only sign-in; old `/login/` gone (AUTH-01)
- [ ] Persistent 90-day session, POST sign-out (AUTH-02)
- [ ] Default-deny login gate with `next` round trip (AUTH-03)

<assumption_delta_decision>
Probe result: detected=true, kind=chosen, term="custom" ("switch to a custom user model and regenerate the initial migrations").
- Primary noun: gifter.User — the project's own user model (AbstractUser subclass) is THE identity everywhere (AUTH_USER_MODEL = "gifter.User").
- Decision: promote. auth.User is not kept alongside with a Profile table; every user foreign key (Wish.user, Wish.claimed_by, and every later model) targets settings.AUTH_USER_MODEL. The Google account (allauth SocialAccount, keyed on Google's stable `sub`) is a detail of how a gifter.User signs in, not a second identity.
- Rationale: there is no production data yet, so promoting now is free; adding alongside would leave auth.User as the FK target forever.
- Invariant test (accepted, cheap): gifter/tests/test_auth.py asserts get_user_model()._meta.label == "gifter.User" and that no model field in any installed app has a relation to a user model other than get_user_model(). It goes red the moment a later phase reintroduces a direct auth.User reference.
- Shape of the identity (username vs email identifier) is confirmed by the checkpoint:decision in Task 2.
</assumption_delta_decision>
