# Plan 03-03: Close the admin channel for a staff giftee (gap closure)

## Phase Goal

> ROADMAP `**Goal:**` (verbatim, not in user-story format): "Members can coordinate who buys what (claim, chip in, mark purchased) and giftees can close wishes once received. A giftee never learns who claimed or contributed, and automated tests enforce this." No user story is invented here. Run `/gsd-mvp-phase 3` if you want one.

Gap closure for 03-VERIFICATION.md (BLOCKER, SC4 / SECR-01). The author is staff and also a giftee. The stock UserAdmin lets him open a user's delete confirmation, and Django's deletion summary lists every cascading row, including `Claim: <wish name>` for the unregistered Claim and Contribution models. The planner probed further as a staff giftee and found a second leak in the same channel, which this plan also closes: the user list accepts `?claims__isnull=False`, `?contributions__isnull=False` and `?claims=<pk>`, which narrows the list to the people who claimed or chipped in. User priority is "usable asap": one small plan, no deploy or human checkpoint, no migration.

<objective>
Make the Django admin tell a staff giftee nothing about claims, prove it with a staff-giftee pass of the secrecy suite, and keep the privacy policy's deletion route workable without admin deletion.

Purpose: closes the 03-VERIFICATION.md gap (SECR-01) and the coverage hole that let it through (SECR-02: the crawl only ran as a non-staff giftee). Extends D-13 (byte-identical giftee responses) and D-14 as amended (protect whether and who, not vocabulary) to the staff giftee.
Output: GifterUserAdmin (delete denied, reverse-relation lookups refused), view-only identity admins, Claim and Contribution string forms without the wish name, StaffGifteeTests, the delete_user command with tests, DEPLOYMENT.md operator steps.
</objective>

Planner-verified at HEAD 38eadd8 (Django 6.1.2, throwaway probe scripts against a test database; nothing in the repo was changed):
- `ModelAdmin._delete_view` checks `has_delete_permission(request, obj)` right after `get_object` and raises PermissionDenied before `get_deleted_objects` runs. With delete denied, every user delete URL, including a nonexistent id such as 999999, returns the same plain "403 Forbidden" body. `delete_selected` has `allowed_permissions = ("delete",)`, so it drops out of `get_actions`: the list loses its action select (no `value="delete_selected"`), a forged POST with `action=delete_selected` re-renders the list with status 200 and deletes nothing, and the change page loses its Delete link. This works for superusers too: the ModelAdmin method is called directly.
- `ModelAdmin.lookup_allowed(self, lookup, value, request)`: `request` is a required argument in 6.1. A lookup with a single relation part is allowed by default, so `?claims__isnull=False`, `?contributions__isnull=False` and `?claims=2` filter the user list (probe: these three are the only staff findings once delete is denied). Two-hop lookups such as `claims__wish__owner` and `user__claims__isnull` on the SocialAccount, EmailAddress and Group lists already return 400. Refusing lookups whose first segment is a reverse relation of User (`field.auto_created and not field.concrete`) turns all of them into 400, while `?is_staff__exact=1` and `?groups__id__exact=1` stay 200. The planner's probe of this shape gave zero snapshot findings over 129 staff probes.
- Reverse relations on User (`User._meta.related_objects`, by name): claims, contributions, created_events, emailaddress, events, logentry, memberships, socialaccount, wishes.
