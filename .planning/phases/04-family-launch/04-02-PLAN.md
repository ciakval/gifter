# Plan 04-02: Nightly backups and a proven restore

## Phase Goal

> ROADMAP `**Goal:**` (verbatim, not in user-story format): "Czech- and English-speaking relatives can use Gifter comfortably on their phones, the data is safely backed up, and a real family dry-run has passed before the 1 Dec freeze." No user story is invented here. Run `/gsd-mvp-phase 4` if you want one.

This plan delivers "the data is safely backed up" (OPS-06, ROADMAP SC4), and the marker that tells the privacy page (plan 04-03) when nightly backups really exist. It runs in wave 1 next to plan 04-01, shares no file with it, and keeps its Docker test runs apart from 04-01's (own image tags, container names and ports). The server-side steps (installing the timer, the drill on a real backup) need the user and are listed as end-of-phase human checks, not checkpoints. Nothing is pushed or deployed by this plan.

<objective>
Ship repo-tracked, locally tested tooling that backs the production SQLite database up every night to a folder outside the app directory on Bombur, keeps 14 days, and restores from a backup either into a throwaway container (drill) or into production (emergency), plus the operator documentation.

Purpose: relatives' wishes and claims must survive a bad deploy, a bad migration or a mistaken deletion before Christmas.
Output: sqlite3 in the image, gifter-backup.sh (including the nightly-backups-since marker), gifter-restore.sh, systemd service and timer, backup-smoke.sh, a SMOKE_TAG override in container-smoke.sh, DEPLOYMENT.md backups section and updated deletion steps.
</objective>

- Whether the deploy user's uid is 1000 was never confirmed (01-04 assumption A1). The container runs as uid 1000 and owns db.sqlite3, -wal and -shm. A host-side sqlite3 run as a different uid cannot write -shm, which a WAL reader needs. Running sqlite3 inside the container through `docker exec` avoids the question entirely, and streaming files through `docker exec cat` (out) and `docker exec -i ... sh -c 'cat > FILE'` (in) creates them with the right owner on each side. `docker cp` would create files as root inside the container.
- The base image python:3.13-slim (Debian 13.7, SQLite library 3.46.1) has no sqlite3 command-line tool: `apt-get install -y --no-install-recommends sqlite3` adds it. The image switches to `USER app` (uid 1000) after collectstatic; the app user can write /tmp.
- sqlite3 behaviour checked with the CLI: `sqlite3 -cmd ".timeout 20000" live.sqlite3 ".backup b.sqlite3"` copies a WAL database and the copy reports journal_mode wal; `sqlite3 b.sqlite3 "PRAGMA journal_mode=DELETE; VACUUM;"` prints "delete" and leaves a single-file database; `PRAGMA integrity_check;` prints "ok"; `sqlite3 -cmd ".timeout 20000" live.sqlite3 ".restore b.sqlite3"` replaces the content of a live WAL database, which keeps journal_mode wal; on a random-bytes file sqlite3 prints "file is not a database" and exits 1.
- settings: the database is DATA_DIR/db.sqlite3 = /app/data/db.sqlite3 in the container, WAL with synchronous NORMAL and timeout 20. The container CMD runs `migrate --noinput` and then gunicorn, so a restart applies migrations to a restored older backup. `manage.py migrate --check` exits non-zero while migrations are unapplied.
